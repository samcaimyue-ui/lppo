## 1. 正本只在一台 Mac 上，没有异地备份

- **证据**：规则 §3「版の記録:ローカルの git」。没有写 remote。GitHub 上的 `samcaimyue-ui/lppo` 停在 10/12，而且是**公开仓库**。
- **风险**：Mac 故障、误删、重装 = v31 全部丢失（34 科的源文件、工具、66 条教训）。线上 Artifact 只有构建结果，丢了源文件就没法再改。
- **建议**：v31 的 git 加一个**私有**远程仓库（GitHub 私有仓库即可），每次发布后 push。不要用公开的 lppo 仓库，因为 reports/ 和批次记录里可能有原文摘录。
- **条文案**：
  > 公開のあと、監督は v31 の git を**非公開**のリモート(GitHub private)へ push する。公開リポジトリ(samcaimyue-ui/lppo)には v31 を入れない。

## 2. 用量没有预算规则，配置偏贵

- **证据**：会话设置为内容部 effort `max`/`xhigh`，UI 部 `xhigh`，改进部 `xhigh`。每个部分配 2 个事实校对（sweep1/2），并反复 RECHECK 直到 0。全体检查约 45 分钟。主人 10/21 用量不足，7 天额度显示警告。
- **建议**（按省得多的排序）：
  1. **按角色定 effort**：监督 `high`；内容 agent `high`；事实校对 `high`；小修（smallfix）`medium`。`max`/`xhigh` 只在新科目的第一批或主人指定时用。
  2. **校对按风险分级**：数值、剂量、分级、禁忌、解剖名等**高风险部分**照旧 2 个校对；纯解说、无数字的部分 1 个校对，RECHECK 只查改过的条目。
  3. **省用量模式**：主人说「省用量」时，这一批内容 agent 只开 1 个、校对 1 个、不做全体检查（只做改动科目的检查），报告里注明「省用量模式」。
  4. **每批开头写预计用量**（大/中/小），超出时先停下问主人。
- **条文案**：
  > 用量の決まり:effort は監督・内容・照合 high、smallfix medium。xhigh/max は新しい科目の第 1 バッチかユーザーの指示のときだけ。照合は数値・分類・禁忌・解剖名を含むパートは 2 人、それ以外は 1 人。ユーザーが「省用量」と言ったら、内容エージェント 1 人・照合 1 人・qa は変わった科目だけ、報告に「省用量モード」と書く。

## 3. 「画面とデータは日本語だけ」的适用范围不清

- **证据**（线上 v70 抽查）：
  - 主页面里仍有中文界面文字：「开始专注」×2、「展开说明」×3、「记牢了」×2、「错题本」×1、「读完了」×2 等，简体中文特征字约 744 处。
  - 基礎運動療法（KIS）的数据里 `zh` 非空 47 处（旧内容）。
  - 规则 §5.8 又说 v59 以前的内容暂不改写。
- **问题**：新加入的 agent 看到「只用日文」，可能会去改旧界面，这违反「一批之内只做这批的事」；也可能照旧界面的中文写新内容，这又违反语言规则。
- **建议**：写清楚三层范围和迁移计划：
  1. **新内容的数据**：只用日文（zh 留空）。现在就执行。
  2. **旧内容的 zh**：留着，不在内容批次里删；以后统一清理。
  3. **界面文字（按钮、提示）**：由 UI 部定一次界面语言，做成一张「界面文字表」一次性替换，不在内容批次里零碎改。
- **条文案**：
  > 言葉の範囲:①新しく作る内容データは日本語だけ(zh は "")。②既存の zh は内容バッチでは消さない。③画面の文言(ボタン・案内)は UI 担当の「画面文言表」で一度に入れ替える。内容バッチで画面の文言を直さない。

## 4. 「OK 过的不返工」和「不能有错误」的优先顺序

- **证据**：§5.7「一度照合と UI の OK が出たものは見直さない」；§5.2「誤りがないこと」；§5.6 的例外（事实错误・版权・显示崩坏）只写在「批次冻结」那条，没写在 §5.7。改进部 10/19 新增了版权相似度检查和事实抽查，必然会查出已经 OK 的旧内容的问题。
- **另一个现成的例子**：セラバンド 的等角（立体风）图解（10/12 做的，线上 v70 仍在）不符合 §5.4「2D、不做 3D・写实」，但按 §5.7 又不该返工。
- **建议**：把例外写进 §5.7，定一个明确的优先顺序，并设「旧规则例外清单」：
- **条文案**：
  > 優先順位:事実の誤り > 著作権 > 画面で壊れて見えるもの > 「OK のものは見直さない」> 見た目の好み。前の 3 つは OK 済みのものでも直す(直すのは該当箇所だけ)。決まりより前に作られて今の決まりに合わないもの(例:セラバンドの等角図解)は STYLE.md の「旧規則例外表」に載せ、直すかどうかはユーザーが決める。

## 5. 角色表只写了 2 个会话，实际有 5 个

- **证据**：§4 只写内容部和 UI 部。实际会话：内容部、ui・ux 和动画项目部、改进部、網站數據分析、云端的规则研究（本仓库）。v70 是 UI 部发布的，v69 是内容部发布的。
- **问题**：
  - 改进部加了新检查，但规则里没有它的权限（能不能改 tools/？能不能发布？）。
  - 谁能改规则文件本身，也没写。
- **建议**：加一张角色表，每个会话写清楚「能改什么 / 能不能发布 / 能不能 commit」，并规定**改规则的流程**：任何会话只能提案，主人同意后由监督改。
- **条文案**：
  > 役の表(全部):内容部=監督(内容・公開・commit)/UI=見た目・図解の決まり・STYLE.md・tools/qa(公開可)/改進部=検査の道具の提案と試作(公開しない)/データ分析=学習データの分析(読むだけ)/規則研究(クラウド)=決まりの改善案(読むだけ・公開しない)。決まりのファイルを変えるのは監督だけ。ほかの役は案を出し、ユーザーの OK のあと監督が入れる。

## 6. 规则没有版本号

- **证据**：§5.6「バッチの間は決まりを凍結」，但规则分散在 7 个文件和 66 条教训里，没有版本号。批次表模板（batches/TEMPLATE）里也没有「用的是哪一版规则」。
- **问题**：批次中途发现新规则时，事后无法核对「这一批按哪一版规则做的」。
- **建议**：给规则加版本号（如 R-2026-10-21），每次改规则 +1 并在 CHANGELOG 写一行；批次表开头写「規則版」。
- **条文案**：
  > 決まりには版番号(R-日付-連番)をつけ、変えたら CHANGELOG に 1 行。バッチ表の最初に、そのバッチの「規則版」を書く。

## 7. 收件方式和主人的习惯不一致

- **证据**：§3「~/Downloads は使わない」。但主人实际是把 PDF 放进下载文件夹，或者传到 Google Drive（10/12 那 4 份就在 Drive 上），也用过 Windows 路径（C:\Users\Admin\Downloads）。
- **建议**：明确「收件箱」：主人放进下载文件夹或 Drive 都可以；监督的第一步是**复制**到 sources/，记下文件名、页数、哈希，**不删除、不移动**原文件。主人只要说「下载文件夹里有新 PDF」就能开工。
- **条文案**：
  > 受け取り口:ユーザーは ~/Downloads か Google Drive に置いてよい。監督は ingest で sources/ へ**写す**(移動・削除しない)、ファイル名・ページ数・ハッシュをバッチ表に書く。
